**API Key**
Access is granted using a key generated by the server as a very long string of characters. The client includes this key in every request, and the server identifies the client because the key is stored in the server's database. When the server finds the key in the database, it grants access to the client's request.

*Advantage:* Easy to implement on the client side – the client simply attaches a key and value to the request.
*Disadvantage:* Low level of security. Its expiration is not limited until it is manually replaced, and if someone captures the key, they have completely free access until the key is changed.

**Basic Auth**
An authentication method that works without a special token. The client attaches their username and password to the request as a single string in the format of username:password. This string is Base64 encoded and sent in the header as follows:

Authorization: Basic dXNlcm5hbWU6cGFzc3dvcmQ=

*Advantage:* Very convenient when working on testing. There is no need to go through the preliminary step of creating a token; you simply log in directly with the username and password.
*Disadvantage:* Credentials are exposed. The information travels across the network freely (since the encoding is easily decoded), making it not secure at all.

**Bearer Token**
The name Bearer means "the holder" – meaning, whoever holds this token is granted access. The client attaches the token to the request as a long string received from the server, inside the Authorization header like this:
Authorization: Bearer <token_string>

*Advantage:* Its security level is high and safe. The token is issued with a short expiration time, so even if it is stolen, it will expire (run out of time) within a few minutes, and the damage will not be too significant. Additionally, the server does not need to connect to the database with every single request to validate the token.
*Disadvantage:* Complexity in temporary revocation. When you want to cancel or block a specific token immediately before its natural expiration time, you will need to implement complex algorithms and mechanisms on the server.

**OAuth2**
This is an entire protocol for managing permissions. It is designed for situations where a user wants to log into a website or application as a third party (an external app), without the external site receiving or seeing the user's actual password.

*Advantage:* Maximum security. There is a complete separation of entities, and it is possible to restrict access only to specific things that the user approves (rather than the entire account).
*Disadvantage:* Very complex to manage and write all the tests for this mechanism due to the multiple steps and redirections between servers.


**Breakdown of the JWT into its Three Parts**
*Header*
Tells the server how to handle the token, what type it is, and which algorithm was run on it for the signature.
*Payload*
The part where the data sits, and this is the JSON that contains the information.
*Signature*
It is created by combining the encoded Header and the encoded Payload + a secret key that exists only at the server. They run an algorithm on this in order to check that all the information remained exactly as it is and did not change when it passed through the network.
**Claim Types**
*1. exp*
This is expiration time. It represents a precise date and time and it keeps the time of the token. When the server receives the token, it checks the current time against the time of the exp; if it is expired, it rejects the request.
*2. sub*
This is the entity they are talking about, and its value is usually the unique identifier of the user in the system. This saves me time when I connect every time with a different request, and because the JWT works on a Stateless state, the server extracts the sub from the token and knows who it is about, and sees that there is access and validity and everything is okay, without checking every time from scratch who is the one performing the action without asking again and again who he is.

**Why You Shouldn't Put Secret Information in the JWT Payload**
The Payload is encoded so that it can be transferred over the network and it is not encrypted, therefore all of its information can be easily retrieved by a simple decode operation. On the other hand, the Signature we talked about is only meant to check if the content arrived whole and that it is not broken, and therefore it still does not encrypt the content and it can be exposed in a moment.

As can be seen in the script – the creation of the server's secret key using the Payload, SECRET, and the HS256 algorithm, and then we receive the token which is a long string divided into 3 parts separated by a dot. The code verifies that the token is indeed divided into 3 parts separated by a dot and that they are all encoded in Base64.

The decoding function basically performs the decode operation – it translates the encoded text using a simple mathematical action without using the secret key at all, proving that the Payload is completely exposed to anyone and is not encrypted.

**session vs token**
The difference between a session and a token is that a token works on a Stateless state and the session works on a Stateful state. If I use a distributed system that has a number of computers communicating with each other in a Stateful manner, then the password (session data) is saved in the database of one of the computers and the second one will no longer recognize it. Letting everyone manage a database for this, where everyone saves the exact same data, is wasteful, inefficient, and very expensive. Therefore, the token is excellent for a distributed system because the token is saved with the client and the server will validate it using the secret key it holds, and the key is not expensive to store on all the computers.
